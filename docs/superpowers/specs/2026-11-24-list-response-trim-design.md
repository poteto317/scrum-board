# ボード・バックログの一覧の応答から説明とソリューションの全文を外す（#120）設計

## 背景

ボードとバックログの一覧（`GET /api/board`、`GET /api/backlog` とその並べ替えの応答）は、全アイテムの説明とソリューション（各最大 10,000 文字）を全文で返していた。カードに表示するのは説明の先頭 3 行だけで、ソリューションは一覧のどこにも出ない。画面は 5 秒ごとに一覧を取り直すので、本文が長いほど転送と画面側の処理が重くなる。

## 決めたこと

- 一覧の応答では、`solution` を空文字にし、`description` を先頭 500 文字（Unicode のコードポイント）に切る。JSON の形は変えない（フィールドは残す）ので、フロントエンドの型は変わらない。
- 切るのは SQL で行う（`LEFT(c.description, 500)` と `''`）。DB から読む量も減る。対象は一覧の形で返す 3 つの読み取り: ボード（`loadBoard`。`Board` / `BoardForProject` が使う）、バックログ（`listBacklogCards`。バックログの取得と並べ替えの応答が使う）、`listOrderedCards`（ボードのカードの並べ替えと、設定変更でカードの位置を詰め直したときの応答が使う）。この 3 つの結果は、位置の更新に ID と位置だけを使い、本文はクライアントへ返すだけで書き戻さない。
- 全文は、これまでどおり詳細の取得（`GET /api/items/{id}`、`/api/items/by-number/{n}`）で返す。書き込みの経路（更新・移動・アーカイブなどが読むカード）は全文のまま。アーカイブ一覧とごみ箱は範囲外。
- 一覧のフィルタ（`list-filter.ts`）は、先頭 500 文字だけを検索する形で割り切る。説明の全文検索のためにサーバー側の検索を足すと、5 秒ごとの取得とフィルタの状態の扱いが複雑になる割に、先頭 500 文字より後ろだけに一致する検索は稀と見る。
- MCP の `get_board` は一覧の応答をそのまま返すので、説明が 500 文字までになり、ソリューションは空になる。ツールの説明と README に書き、全文は `get_item` で取る。
- 画面の表示（`board.css` の 3 行の省略）は変えない。500 文字は、3 行の表示に足りる量として決めた値（実測はしていない）。
- 実装プランは作らない。変更が、SQL の列の差し替えと、テスト・MCP の説明の更新だけで小さいため。
- 画面の一覧のアイテムを編集の元にする経路は無い（編集は詳細で全文を取り直す）。一覧の切り詰めた説明が書き戻されることはない。

## 受け入れ条件

1. ボード・バックログの一覧で、`solution` が空、`description` が 500 文字以内になる。
2. 詳細の取得（番号・ID）は全文を返す。
3. MySQL: `Board` / `Backlog` の説明が `LEFT` と一致する（`KANBAN_TEST_DSN` 指定時）。
4. 既存のテストが通る。

## 範囲外

- 説明の全文検索のサーバー側の実装。
- アーカイブ一覧・ごみ箱の応答の軽量化。
- 一覧の応答に「切り詰めた」印を足すこと。
