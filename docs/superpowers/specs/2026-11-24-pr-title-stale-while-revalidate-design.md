# PR のタイトルの取得で、ポーリングが GitHub を待たないようにする（#125）設計

## 背景

アイテム詳細は 5 秒ごとにアイテムを取得し、そのたびにサーバーが PR のタイトルを `PRTitleResolver.Resolve`（`backend/internal/kanban/pr_title.go`）で解決する。キャッシュは、成功が 10 分、失敗が 1 分。期限が切れた URL では、その呼び出しが GitHub の応答（最大 2 秒）を待ってから返っていた。失敗する URL（非公開リポジトリの 404、レート制限、タイムアウト）では、1 分ごとに、ポーリングの 1 回が 2 秒待たされる。同じ URL への同時の呼び出し（複数のタブ、一括取得と詳細）は、それぞれ GitHub に問い合わせていた。一括取得 `POST /api/pr-titles`（最大 50 件）は、1 件ずつ順番に取りに行っていた（各最大 2 秒）。

カードに書かれた「失敗を保存しない」「上限なし」「並行なし」のうち、失敗の保存（1 分）、キャッシュの上限（512 件）、GitHub への同時リクエストの上限（8）は、すでに入っている。今回は、残りを足す。

## 決めたこと

- **期限が切れた値も、すぐ返す（stale-while-revalidate）。** `Resolve` は、キャッシュにあれば（期限切れでも）その値を返す。期限切れなら、バックグラウンドで GitHub に取りに行き、次の呼び出しから新しい値が出る。待つのは、一度も見たことのない URL の最初の 1 回だけで、呼び出し元の `ctx` に加えて `firstWait`（3 秒）で打ち切る（その後も取得は続き、答えはキャッシュに入る）。これで、失敗する URL があっても、ポーリングのたびに GitHub を待たず、問い合わせは期限（失敗は 1 分、成功は 10 分）ごとに 1 回になる。
- **更新に失敗しても、最後に取れた本物のタイトルを残す（stale-if-error）。** 期限切れの更新が失敗したとき、フォールバック（`owner/repo#n`）で上書きせず、前のタイトルを失敗の期限（1 分）で持ち直す。GitHub の一時的な失敗で、表示がタイトルから番号に戻るのを避ける。ただし、最後に GitHub が確認してから `prTitleStaleMaxAge`（1 時間）を超えたら残さず、フォールバックに戻す（PR の削除・リポジトリの非公開化・トークンの失効で、古いタイトルが出続けないようにするため）。
- **同じ URL への同時の取得を 1 つにまとめる。** 取得中の URL は、`inflight` に持ち、2 つ目以降の呼び出しは同じ取得の完了を待つ（または期限切れなら待たずに返す）。取得は、呼び出し元とは別のゴルーチンで動かす。リクエストが終わっても、答えはキャッシュに入る。取得の開始時に、キャッシュを確認し直す（確認から開始までの間に答えが入った場合に、重複して問い合わせない）。ゴルーチンの中の panic でも、取得中の印を必ず外す。
- **一括取得を並行にする。** アクセスの確認（データベース）は 1 件ずつ、確認の通った URL の解決は並行（`resolvePRTitleLabels`。GitHub への同時リクエストは既存の上限 8）。アイテムの `prTitles` の付与も、同じ関数を使う。
- **GitHub への同時リクエストの上限（8）の待ちは、GitHub の失敗として数えない。** スロットを待つ時間（`slotWait`、既定 4 秒）と、リクエストの時間（`prTitleAPITimeout`、2 秒）は別に数える。スロットが取れずに諦めたときは、何もキャッシュせず、次の呼び出しがすぐ取り直す。
- **期限切れのエントリは、上限に達するまで残す。** 期限切れでも返せるように、保存のたびに消さない（上限 512 に達したら、期限切れから先に消し、それでも足りなければ任意の 1 件を消す。消えた URL は、次の呼び出しが「初めて見る URL」として待つ）。
- 一括取得・アイテム取得のどちらも、アクセスの確認の仕組み（#98）と、応答の形は変えない。

## 受け入れ条件

1. 期限切れのタイトルは、GitHub の応答を待たずに返り、バックグラウンドの更新の後に新しいタイトルが返る（`TestPRTitleResolverServesAnExpiredTitleWithoutWaitingForGitHub`）。
2. 期限切れの失敗（フォールバック）も、待たずに返る（`...ServesAnExpiredFailureWithoutWaitingForGitHub`）。
3. 更新が失敗しても、最後の本物のタイトルを返し、失敗は短時間キャッシュされる（`...KeepsTheLastTitleWhenARefreshFails`）。
4. 同じ URL への同時の呼び出しで、GitHub への問い合わせは 1 回（`...SharesConcurrentFetchesOfOneURL`）。
5. 一括取得は、URL を並行に解決する（`TestBatchPRTitlesResolvesURLsConcurrently`）。
6. 古いタイトルは、更新に失敗し続けて 1 時間を超えたらフォールバックに戻る（`...DropsAnOldTitleWhenRefreshesKeepFailing`）。
7. スロット待ちで諦めたものは、キャッシュされず、すぐ取り直せる（`...DoesNotCacheWaitingForASlotAsAGitHubFailure`）。
8. 取得が panic しても、その URL が取得中のまま残らない（`...ReleasesAURLWhenTheFetchPanics`）。
9. 呼び出し元が諦めても、答えはキャッシュに入る（`...FillsTheCacheEvenWhenTheCallerGivesUp`）。確認から開始までの間に答えが入ったら、問い合わせない（`...DoesNotAskAgainWhenAnAnswerArrivedMeanwhile`）。
10. キャッシュは上限（512）を超えない（既存の仕様。期限切れは、満杯のときだけ先に消える）。アイテムの `prTitles` の付与も、一括取得と同じ並行の解決を使う（既存の `TestGetItemEnrichesPRTitles`、`TestGetItemByNumberEnrichesPRTitles`）。
11. 初めて見る URL を待つのは `firstWait` まで（`...StopsWaitingForAFirstAnswerAfterFirstWait`）。同じ URL を同時に聞かれたら、同じ取得を共有する（`...HandsOutOneFlightPerURL`）。
12. 既存のタイトル解決のテスト（成功のキャッシュ、404 の短時間キャッシュ、タイムアウト、空のタイトル、トークンが出力に出ない）が通る（成功のキャッシュ、404 の短時間キャッシュ、タイムアウト、空のタイトル、トークンが出力に出ない）。

## 範囲外

- 失敗の再取得の間隔の指数的な伸ばし、403/429 の `Retry-After` の尊重。再取得は、これまでと同じく失敗 1 分に 1 回で、今回は悪化しない（1 つの URL でトークンなしの上限は毎時 60 回）。
- バックグラウンドの更新が、Cloud Run の既定の CPU 割り当て（リクエスト中だけ）では、リクエストの後に止まりうる。止まった更新は、次のリクエストで再開するか、2 秒の期限で失敗として 1 分キャッシュされる。どちらも従来（期限切れのたびに失敗）より悪くならない。CPU を常に割り当てる（`--no-cpu-throttling`）かどうかは、費用に関わるデプロイの判断として、ここでは変えない。

- キャッシュの上限の見直し（セキュリティの #98 とあわせて検討する、とカードにある。上限 512 は入っている）。
- プロセスをまたぐキャッシュ（再起動で空になる）。
- 初回（一度も見たことのない URL）のポーリング以外の待ち。

## 実装プラン

変更は `pr_title.go` と `handler.go` の 2 か所に収まるため、実装プランは作らず、設計書のサブエージェントレビューも省く。
