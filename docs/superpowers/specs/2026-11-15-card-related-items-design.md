# カード関連アイテム設計（カード #28）

## 背景

カード同士や、アプリ外のページ URL を「関連」として付けたい。現状は GitHub PR URL（`prUrls`）だけが外部参照で、他カード参照や任意 URL はない。

カード説明: 他のアイテムを関連に入れられるようにしたり、このアプリとは関係ない別のページの参照、URLなどを関連として付けられるようにする。

## 決めたこと

| 事項 | 採用 |
|------|------|
| 関連の種類 | **他カード（公開 TASK 番号）＋任意の http(s) URL** |
| 向き | **双方向**（カード↔カード）。URL は **片方向**（付けたカードのみ） |
| API | カード JSON の `relatedItems` ＋ `PATCH` での **全置換**（`prUrls` と同型） |
| ラベル | **任意**。空ならカードは相手のタイトル、URL はホスト名（取れなければ URL 全文） |
| 履歴 | `prUrls` と同様に `relatedItems` を変更履歴の対象にする（相手側の自動同期も含む） |
| 表示 | **カード詳細のプロパティ欄**（GitHub PR の下）。ボード上のバッジは v1 対象外 |
| 上限 | **なし**（件数制限を設けない） |
| PR リンク | **既存 `prUrls` を維持**。関連へ統合・移行しない。同一 URL を両方に持ててもよい |

## 用語

- **関連アイテム**: あるカードに紐づく「他カード」または「外部 URL」の1件。
- **カード関連**: 種類がカード同士のもの。無向の関係として両端のカードに見える。
- **URL 関連**: 種類が外部 URL のもの。付けたカードにだけ見える。

## データモデル

補助表 `card_related_items`（起動時マイグレーションで `CREATE TABLE IF NOT EXISTS`。既存 `card_pr_links` と同方針）:

| 列 | 内容 |
|----|------|
| `card_id` | 所有者カード（FK → `cards.id` ON DELETE CASCADE） |
| `position` | そのカード内の表示順（0始まり） |
| `kind` | `'card'` \| `'url'`（ASCII） |
| `related_card_id` | `kind='card'` のとき相手カード ID（FK → `cards.id` ON DELETE CASCADE）。URL 時は NULL |
| `url` | `kind='url'` のとき URL（`VARCHAR(2048)` ascii_bin）。カード時は NULL |
| `label` | 任意表示名（`VARCHAR(120)` utf8mb4、DEFAULT `''`） |

制約:

- `PRIMARY KEY (card_id, position)`
- `kind='card'` のとき `related_card_id IS NOT NULL` かつ `url IS NULL`
- `kind='url'` のとき `url IS NOT NULL` かつ `related_card_id IS NULL`
- 同一カード内で `related_card_id` の重複不可（UNIQUE、NULL は複数可のため MySQL の UNIQUE は URL 側と分けてアプリ検証でも可。実装は `UNIQUE(card_id, related_card_id)` と `UNIQUE(card_id, url)` を張る）
- 自己参照禁止（`card_id ≠ related_card_id`）はアプリ検証。DB CHECK は任意

**双方向の格納:** カード関連は **両方向に1行ずつ**持つ（A→B と B→A）。ラベルは **各方向で独立**（A 側だけラベル付き、B 側は空、があり得る）。URL 関連は所有者カードの行のみ。

相手カード削除時: FK CASCADE で両方向の行が消える。

## API

### JSON 形

カードに追加:

```json
"relatedItems": [
  { "kind": "card", "number": 12, "title": "相手のタイトル", "label": "" },
  { "kind": "url", "url": "https://example.com/docs", "label": "仕様" }
]
```

- 読み取り時 `kind=card` は公開番号・現行タイトルを付与する（タイトルは表示用。保存しない）。
- 書き込み時クライアントは `kind=card` なら `number`（正の整数）、`kind=url` なら `url`、任意で `label` を送る。`title` / 内部 id は無視してよい。
- 欠落時は常に `[]`（null にしない）。`GET /api/board` にも載せるが UI は詳細のみ（`prUrls` と同様）。

### PATCH

`PATCH /api/cards/{id}` の任意フィールド `relatedItems` で **そのカード視点の一覧を全置換**。

- **キー省略**: 関連を触らない（`prUrls` と同じ）。
- **`null`**: `prUrls` と同じ扱いとする（サーバが拒否するなら 400。クリア手段は空配列 `[]`）。クライアントはクリアに `null` を送らない。L-454: 省略を undefined マージで消さない。

**置換の意味（カード関連・双方向）:**

1. リクエストの `relatedItems` を検証・正規化したあと、対象カード A の行をすべて削除し、新しい順序で挿入する。
2. **追加された**相手カード B について、B→A 行が無ければ B の末尾に `kind=card`・空ラベルで挿入する。
3. **外された**相手カード B について、B→A 行を削除し、B 側の `position` を詰める。
4. 既に B→A がある相手を維持する場合、B 側のラベル・順序は **変えない**（A の PATCH は A 側の順序・ラベルだけ更新）。

URL 関連は A の行だけの置換で足りる（相手カードなし）。

**トランザクション:** A の置換・相手の逆方向挿入／削除・position 詰め・A/B の `updatedAt`・A/B の履歴は **同一トランザクション**。失敗時はすべてロールバック（片側だけ残さない）。

**ロック:** 触るカード行（A と、追加／削除対象の相手）を `cards.id` 昇順で `SELECT ... FOR UPDATE` してから `card_related_items` を更新する（相互リンク時のデッドロック防止。複数 PR リンク設計と同趣旨）。

同一リクエスト内で同じ `number` や同じ正規化 URL が重複したら 400。自己参照・存在しない番号・不正 URL・ラベル超過も 400。空配列は「関連なし」で有効。

検証:

- URL: trim のみ（末尾スラッシュやホストの大小は正規化しない）。trim 後 `http://` または `https://` で始まること。最大 2048。改行・空白のみ不可。GitHub 限定はしない。重複判定・保存値はともに **trim 後の文字列**。
- ラベル: trim。最大 120。空文字可。
- カード番号: 正の整数で、存在する公開番号。自分自身は不可。

成功時レスポンスのカードは、置換後の `relatedItems`（タイトル付き）と `updatedAt` を含む。相手カードの `updatedAt` も、逆方向の挿入・削除があった場合は更新する（履歴の `occurredAt` と揃える）。

### 履歴

`historyValues` / 差分フィールドに `relatedItems` を追加する。値は正規化した JSON 文字列（並び・kind・number または url・label。title は含めない＝表示用の揺れで偽差分を出さない）。

- A の PATCH で A に履歴を書く（既存 `appendHistory`）。
- 逆方向の自動追加・削除で B の `relatedItems` が変わった場合、**同じトランザクション内で B にも履歴**を書く（kind は通常の更新と同じ `"update"`）。before/after は B 視点の一覧。

フロントの履歴表示は `prUrls` と同様にフィールド名を日本語ラベル化する（例: 「関連」）。中身は JSON のまままたは簡潔な要約でよいが、少なくとも差分として見えること。

**履歴インポート**（`import-history`）への `relatedItems` 追加は **v1 対象外**（画面・API の通常更新履歴のみ）。

## UI（カード詳細）

プロパティ欄・GitHub PR ブロックの下に「関連」セクション:

- 一覧: 各行に表示ラベル（label があればそれ、なければカードタイトル / URL ホスト名）、種類に応じたリンク
  - カード: アプリ内 `/cards/{number}`（`RouterLink` または同等）
  - URL: `target="_blank"` `rel="noopener noreferrer"`
- 追加: 1つの入力。内容が正の整数だけならカード番号、`http(s)://` なら URL、それ以外はエラー。任意ラベル用の第2入力（空可）。追加は即 PATCH（`CardPrLinks` と同型のセッション）。
- 削除: 行ごとの削除 → 即 PATCH（双方向のため相手からも消える）。
- 保存中は追加・削除を無効化。失敗は既存のエラー表示。タイトル／説明のオートセーブとは分離（`card-autosave` の対象外）。

ボード・バックログのカード面への表示はしない（v1）。

## 対象外（v1）

- 双方向の「相手側ラベル」編集 UI（相手カード詳細を開けば編集可）
- ボード上バッジ、検索、関連グラフ
- ファイル添付、非 http(s) スキーム
- `prUrls` との統合・移行
- 関連の並び替え専用 DnD（追加順＝position。削除で詰める）

## 受け入れ条件

1. カード詳細から他カードの公開番号を関連に追加でき、追加直後に相手カード詳細の関連一覧にも自分が現れる。
2. 外部 http(s) URL を関連に追加でき、リンクで開ける。相手カードには現れない。
3. ラベル空ならカードはタイトル、URL はホスト名（または URL）で表示される。ラベルありならそれを優先する。
4. 関連を外すと、カード関連の場合は相手側からも消える。
5. `PATCH` で `relatedItems` を省略した更新は既存の関連を消さない。
6. 自己参照・重複・不正 URL・存在しない番号は保存されずエラーになる。
7. 関連の追加・削除がカード履歴に残り、相手側の自動同期分も相手の履歴に残る。
8. 既存の `prUrls`・コマンド・オートセーブは回帰しない。

## 知見（実装時に見る）

- **L-001 / L-002**: 保存失敗を成功扱いしない。一覧取得失敗を空配列とみなして置換しない。
- **L-035**: 削除は一覧インデックスではなく、確定した number/url で次の配列を組む（または保存応答で差し替える）。
- **L-037**: 保存中にカード切替したらリクエストをキャンセルし、古い応答を適用しない（`CardPrLinks` の `cancel$` と同じ）。
- **L-453 / L-454**: 関連 PATCH とタイトル等を連続で独立保存するとき、片方のレスポンスで他方を消さない。`relatedItems` 省略時に null/undefined で消さない。
- **L-688**: 削除確認モーダルは必須にしない（PR リンクと同様の即削除）。破壊範囲は関連行のみ。
