# 一覧フィルタリング（アイテム #23）

## 背景

かんばんとプロダクトバックログに絞り込みが無く、アイテムが増えると目的のカードを探しにくい。カード要件は、名前（タイトル優先・説明も候補）とステータスでの絞り込み、状態のサーバー保存、端末間で同じ表示。

## 決めたこと

| 事項 | 採用 |
|------|------|
| 保存の単位 | **ワークスペース共通 1 件**（1A）。Basic Auth 共有前提で「どの端末でも同じ」を満たす |
| ボードとバックログ | **同じフィルタ状態**を両方に適用（2A） |
| ステータス | **列の複数選択**。未選択（空配列）＝全列（3A） |
| テキスト | **大文字小文字無視の部分一致**。タイトル **または** 説明にヒットで表示（4A）。初版は並べ替えによるタイトル優先はしない（ヒット有無のみ） |
| 適用場所 | **FE がクライアント側で絞る**。API はフィルタ状態の永続化のみ（5A） |
| 初版対象外 | 担当者・関連・PR URL のフィルタ、サーバー側クエリ絞り込み、ユーザー別 prefs、ローカル専用保存（6A） |

## 目的と受け入れ条件

1. ボードとバックログの両方に、テキスト入力とステータス（列）複数選択の UI がある。
2. テキストはタイトルまたは説明への部分一致（大小無視）。空文字はテキスト条件なし。
3. ステータスは選択した `columnId` のいずれかに属するアイテムのみ表示。選択なし＝全ステータス。
4. テキストとステータスは **AND**（両方指定時は両方満たすものだけ）。
5. フィルタ状態はサーバーに保存され、別端末・再読込でも同じ状態が適用される。
6. ボード／バックログのライブ更新で一覧が差し替わっても、現在のフィルタが再適用される（保存し直さない限り prefs は変えない）。
7. 不正な保存データ（壊れた JSON・未知フィールド・非配列の statusIds 等）ではクラッシュせず、**空のフィルタ（全件表示）として扱い、壊れた値を空オブジェクトで上書きしない**（読み取り時。書き込みは検証付き）。
8. **GET `/api/list-filter` の通信失敗**は空フィルタ成功と同一視しない。エラー表示し、直前のメモリ上のフィルタ（未取得なら全件表示のまま）を保つ。再試行できる。
9. フィルタ UI の操作で DnD・並べ替え・作成・詳細遷移を壊さない。非表示アイテムは操作対象に出さない。
10. クリア操作でテキストとステータス選択を消し、サーバーにも空状態を保存する。
11. フィルタの GET／PUT 応答には世代ガードを付け、古い応答で新しい入力や新しい GET 結果を上書きしない（L-037 / L-040）。

## 永続化（API）

キーはワークスペースに 1 つ。

| メソッド | パス | 挙動 |
|----------|------|------|
| `GET` | `/api/list-filter` | `{ "query": string, "statusIds": number[] }`。行が無ければ `{ "query": "", "statusIds": [] }` |
| `PUT` | `/api/list-filter` | 同上の JSON を全体置換。検証後に保存し、保存後の正規化済み JSON を返す |

検証（PUT）:

- `query`: string。未指定／null は 400。前後空白は trim。最大長 **200**（超過は 400）。
- `statusIds`: number の配列。未指定／null は 400。空配列可。要素は有限の正の整数のみ（非 number・NaN・≤0 は 400）。重複は除去して保存。
- **存在しない columnId は無視して正規化**（存在する ID だけ残す。全て無効なら `[]`＝全列表示）。列削除後も 400 にせず壊れない。
- 未知のトップレベルキーは 400（既存 API 慣習に合わせる）。

ストレージ: 単一行テーブル（例: `workspace_list_filter`）または key-value 1 行。マイグレーションで作成。

**適用時の statusIds:** GET で得た `statusIds` を画面に載せるとき、および `itemMatchesFilter` で使うとき、**現在の列一覧に無い ID は無視**する（残った ID が空ならステータス条件なし＝全列）。DB の生値は GET 失敗扱いにせず、表示正規化のみ。任意で次回 PUT 時に正規化後を書き戻してよいが必須ではない。

## クライアント挙動

- 起動／ボード・バックログ表示時に `GET /api/list-filter` を取り、signals に載せる。
- テキスト入力は **300ms デバウンス**後に `PUT`。ステータス切替も **同じ 300ms デバウンス**で `PUT`（連打・連続チェックをまとめる）。
- 保存は **成功後にサーバー応答で signals を更新**する方式（楽観更新しない）。失敗時はエラー表示し、直前の成功状態を保つ。
- 純関数 `itemMatchesFilter(item, filter)` で判定（statusIds は呼び出し側で現行列に正規化して渡してもよい）。ボードは列内の表示リストをフィルタ後の配列にする。バックログも同様。件数表示は **フィルタ後** を出す（ツールバー等）。
- 共有モジュール（例: `list-filter.ts` + API クライアント／小さな session サービス）をボード／バックログから利用。

## UI（方針）

- ボード: ツールバー付近に検索欄＋ステータス用の複数選択（チェックリストまたは同等）。
- バックログ: 見出し付近に同等の UI。
- 「クリア」で全解除。
- アクセシブルな label / キーボード操作。見た目は既存の toolbar／フォームに揃える（新デザインシステムは作らない）。

## 知見（実装時）

- L-001: PUT／クリアの成否を見てから成功扱い。失敗時に prefs を空にしない。
- L-002: GET 失敗と「空フィルタ」を取り違えない。壊れた DB 値を空で上書きしない。
- L-037 / L-040: フィルタ取得・保存の世代ガード。古い応答で新しい入力を上書きしない。
- L-056: 本機能はブラウザストレージを使わないため **該当なし**。API／壊れた DB JSON は受け入れ条件 7・8 で扱う。

## 対象外

- 担当者・タグ・関連・PR によるフィルタ
- サーバー側の一覧クエリ絞り込み
- ユーザー別・端末別 prefs
- タイトル一致を上に並べ替える関連度ソート（初版）
- URL クエリとの双方向同期
