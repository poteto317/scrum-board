# Close 列も自動アーカイブして、終わったアイテムが増えても重くならないようにする（#128）設計

## 背景

ボードとバックログは、アイテムをすべて取得して描画する。Done は、`done_at` から 10 日経つと毎日のジョブ（`POST /api/archive/auto-archive`）でアーカイブされ、ボードの取得から外れる（`c.archived_at IS NULL`）。一方 Close は対象外で、閉じたアイテムが増え続けるため、初期表示とポーリングの量が際限なく増える。

カードの案は「Done / Close の最新 N 件だけ表示」か「終わったアイテムを既定で返さない」。確認の結果、Done が既にアーカイブで有界になっているため、Close にも同じ仕組みを当てる方針にした（ユーザーの選択）。サーバーの最新 N 件の制限は、並び替え・バックログ・MCP への影響が大きいので採らない。

## 決めたこと

- **「終わった列」= Done または Close**（`isFinishedColumnName`）。`done_at` は、外から終わった列に入った時刻で、終わった列どうしの移動では変えず、終わった列から出たら消す。
  - 対象: 作成、`UpdateItem`、`ReorderItems`（`planCardReorder`）、ゴミ箱からの復元、アーカイブ候補、マイグレーションの埋め戻し（`done_at` が NULL の既存の Close は、最新の履歴の時刻か `updated_at`）。
- アーカイブ候補は、Done または Close で、`done_at IS NULL OR done_at <= 期限`（10 日）。実質の終了時刻は、`done_at` と、終わった列への最新の遷移履歴の遅い方（既存の規則どおり）。
- **解除（復元）は元の終わった列へ戻す。** その列が無ければ Done。復元の時刻を `done_at` にし、列の末尾に置く。
- スプリントの速度（Done の名前判定）は変えない。
- 画面の文言は「Done・Close」「元の列へ戻す」に直す。

## 受け入れ条件

1. Close に入ると `done_at` が付き、出ると消える。Done↔Close の移動では変わらない。並び替えで Close へ入る場合も同じ。
2. 10 日を過ぎた Close のアイテムは自動アーカイブされ、Done / Close 以外の列は、`done_at` が古くても対象外。
3. 既存の Close の `done_at` が NULL のものは、起動時の埋め戻しで値が入る。
4. Close のアーカイブを解除すると、Close に戻る。
5. 終わったアイテムが増えても、ボードの取得量は、直近 10 日分で頭打ちになる。

## 運用への影響

デプロイ後の最初の自動アーカイブで、10 日より古い既存の Close がすべてアーカイブされる（`/archive` から解除できる）。

## 範囲外

- 最新 N 件の制限、「もっと見る」、終わったアイテムを既定で返さない API の変更。
- アーカイブまでの日数の変更や、Done と Close で別の日数にすること。

## レビューで決めたこと

- Done↔Close の移動は新しい終了ではない。実質の終了時刻の履歴は、終わった列の**外から**入った遷移（`Before` が終わった列でない）だけを数える。数えると、Done で 9 日経ったものを Close へ動かすたびに 10 日のタイマーが戻ってしまう。
- ゴミ箱から戻したものは、これまでの Done と同じく `done_at` を保つ。古い終了時刻のまま戻した Close は、次の自動アーカイブで対象になる（Done と同じ挙動。変えない）。
